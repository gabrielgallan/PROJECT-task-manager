# Backend Status

Last reviewed: 2026-09-01.

This document is the canonical inventory of backend coverage required by the current frontend prototype. It describes the implementation that exists today and the remaining work; it is not evidence that an unchecked contract has already been finalized.

## How to read this document

- A checked route is wired through every runtime layer required to serve the request.
- **Domain** means the use case and its application ports exist.
- **HTTP** means controller, validation, error mapping, presentation, authentication, and module wiring are usable.
- **Persistence/infra** means the production adapters required by the use case are registered.
- **Tests** identifies existing automated coverage. Unit coverage alone does not make a route operational.
- A partially implemented route stays unchecked even when one or more child layers are checked.

All routes use the `/api` prefix. All non-public resources belong to the authenticated user.

## Shared contract

- IDs and timestamps are generated by the backend. Public date-times use ISO 8601 and persisted instants use UTC. Calendar-day rules receive a valid IANA timezone from the client and never reinterpret stored instants.
- Task, Category, Plan, and Work Log are independent user-owned resources.
- Plans and Work Logs may optionally reference a Task and a Category.
- Deleting a Task or Category retains related Plans and Work Logs and clears the deleted reference.
- Multiple values inside one filter facet use OR; different facets combine with AND.
- UI-only filter sentinels such as `none`, `no-task`, and `no-category` must be translated at the API boundary and never treated as IDs.
- Rules already enforced by the frontend must also be enforced by the backend when the corresponding route is implemented.
- The HTTP layer must map both an absent resource and a resource owned by another user to the same `404` response. Domain use cases keep `ResourceNotFoundError` and `NotAllowedError` distinct internally.

`GET /api/work-logs` requires `from` and `to`, accepts the same Task/Category filters as Plans, orders by start time, and includes Task and Category summaries.

Creation, editing, and rescheduling must enforce all of these rules:

- end is after start;
- start and end are on the same calendar day in the supplied IANA timezone;
- end is not in the future;
- the half-open interval does not overlap another Work Log owned by the user.

All four rules are enforced by `CreateWorkLogUseCase` and `EditWorkLogUseCase`, and the edit path excludes the edited Work Log from its own overlap check.

A violated rule returns `400` carrying the use-case message; the overlap error reports the conflict without identifying the conflicting Work Log. Suggested “Log now” ranges and untracked-minute calculations remain client-side derived behavior and do not need endpoints.

Every Work Log route maps both `ResourceNotFoundError` and `NotAllowedError` to a `404`, so a Work Log owned by another user is indistinguishable from a missing one; on `POST /api/work-logs` that same `404` reports a missing or foreign referenced Task or Category. `timeZone` is required on both write routes because the use case revalidates the calendar day of the resulting interval on every write.

`POST /api/work-logs` returns the created Work Log under `data` with its raw `taskId`/`categoryId`, presented by `WorkLogPresenter.toHTTPCreated`. The `task`/`category` summaries belong to the fetch payload, which builds them from the `WorkLogData` value object.

The decisions behind the current shape of these routes are recorded in `docs/specs/02-work-logs-http-contract-refinement.md`.
